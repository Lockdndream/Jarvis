# Jarvis — Local Laptop Assistant

Minimal prototype of a local AI assistant with a mobile-friendly web UI.

## Setup (Windows PowerShell)

```powershell
# 1. Create virtual environment
python -m venv venv

# 2. Activate it
.\venv\Scripts\Activate.ps1

# 3. Install dependencies
pip install -r requirements.txt

# 4. Start the server
uvicorn app.main:app --host 0.0.0.0 --port 8000

# 5. Find your laptop's local IP (in a new terminal)
ipconfig | findstr /i "IPv4"

# 6. Open from your phone browser
# http://<LAPTOP_IP>:8000
```

## Voice, Push Notifications, and PWA (Milestone 7)

Voice input (microphone), service workers, and Web Push all require a
"secure context": HTTPS, or the special-cased `http://localhost`. Plain
`http://<laptop-ip>:8000` from a phone is neither, so those features won't
work until you enable local HTTPS.

```powershell
# 1. Generate a local self-signed certificate (git-ignored, per machine)
python scripts/generate_dev_cert.py

# 2. Run uvicorn with TLS
uvicorn app.main:app --host 0.0.0.0 --port 8443 --ssl-keyfile key.pem --ssl-certfile cert.pem

# 3. On your phone, browse to https://<LAPTOP_IP>:8443
#    Accept the "not secure" warning once — this is expected for a
#    self-signed cert. Once accepted, mic/service-worker/push all work.
```

Prefer [mkcert](https://github.com/FiloSottile/mkcert) over the self-signed
fallback if you want to avoid the browser warning entirely: `mkcert
<laptop-ip> localhost 127.0.0.1`, then point `--ssl-keyfile`/
`--ssl-certfile` at the files it produces instead.

To enable Web Push (optional — in-app/foreground notifications work
without it):

```powershell
python scripts/generate_vapid_keys.py
# copy the two JARVIS_VAPID_* lines it prints into your .env, then restart
```

Then tap the 🔔 button in the header to opt in from your phone. See
`SESSION.md` → Milestone 7 for the full capability matrix and architecture
decisions.

## Commands

| Command                    | Description                                      |
|----------------------------|--------------------------------------------------|
| `/status`                  | Show hostname, OS, time, Python                  |
| `/processes`               | List top running processes                       |
| `/pwd`                     | Show current working directory                   |
| `/demo-task`               | Start a 15-second demo task                      |
| `/tasks`                   | Show running and recent tasks                    |
| `/cancel <id>`             | Cancel a running task by task ID                 |
| `/mock-agent`              | Start a mock interactive agent (asks a question) |
| `/answer <qid> <answer>`   | Answer a pending question by question ID         |
| `/attention`               | Show summary of all tasks waiting for user       |

Any other message is echoed and stored but not executed.

## Task System

Jarvis can run supervised long-running subprocesses:

- Each task gets a unique `task_id` (UUID) and is tracked in SQLite
- Stdout/stderr is streamed line-by-line to all connected WebSocket clients
- Multiple clients all receive the same task events in real time
- On reconnect, the client restores history and learns about running tasks
- Active Tasks panel shows name, elapsed time, latest output line, and a Cancel button
- `/cancel <task_id>` terminates the process and updates state
- On server shutdown, all running processes are terminated; on startup, tasks left as `running` are marked `failed`

Task events use structured JSON content:
```
{
  "type": "task_stdout",
  "timestamp": "2026-07-08T00:47:00Z",
  "content": "{\"task_id\": \"<uuid>\", \"name\": \"Demo Task\", \"line\": \"Progress 5/15\"}"
}
```

## Question Protocol

Tasks that need user input emit a structured line on stdout:

```
JARVIS_QUESTION:{"question_id":"<uuid>","question":"Which approach should I use?","options":["A","B"],"context":"A is faster. B is safer."}
```

Fields in the JSON payload:

| Field        | Required | Description                            |
|--------------|----------|----------------------------------------|
| question_id  | yes      | UUID string, generated by the worker   |
| question     | yes      | The question text displayed to the user|
| options      | no       | Array of answer choices (e.g. ["A","B"])|
| context      | no       | Additional context shown to the user   |

### Detection and parsing

`app/protocol.py` scans each stdout line for the `JARVIS_QUESTION:` prefix. If the subsequent JSON is valid and contains the required fields, it returns a structured dict. Malformed or missing-field lines are silently ignored.

### Lifecycle

1. Worker writes `JARVIS_QUESTION:` line → `task_manager.py` parses it
2. A `question_asked` event is broadcast to all WebSocket clients
3. Task transitions from `running` → `waiting_for_user`
4. The raw protocol line is **not** emitted as a `task_stdout` event (filtered out)
5. The question is persisted in the `questions` SQLite table with status `pending`
6. The UI displays it in the **Needs Your Attention** section with option buttons and a custom answer input
7. User sends answer via `/answer <question_id> <answer>` or by clicking an option button in the UI
8. Answer is written to the worker's stdin; `question_answered` event broadcast; question status → `answered`
9. Task returns to `running`
10. Worker reads the answer from stdin and continues its logic

### Cancellation during waiting_for_user

If a task is cancelled while in `waiting_for_user`:

- The pending question status → `cancelled`
- A `question_cancelled` event is broadcast
- The UI removes the question from Needs Your Attention
- The process is terminated
- On reconnect, cancelled questions are **not** restored

### Reconnection restoration

On WebSocket reconnection, the server sends:

- **Event history** (last 100 events)
- **Running tasks** — current state of each task (`running` or `waiting_for_user`)
- **Pending questions** — only questions with status `pending` (not `answered` or `cancelled`)

This ensures that if the browser disconnects while a task is waiting for an answer, the question reappears on reconnect.

## Architecture

```
app/
  main.py               FastAPI server, WebSocket endpoint, routing
  connection_manager.py  WebSocket broadcast to all connected clients
  task_manager.py        Async subprocess lifecycle (start, monitor, cancel, stdin write, question detection)
  database.py            SQLite persistence (sqlite3 — events + tasks + questions tables)
  models.py              Event dataclass, type constants, task status constants
  executor.py            Command execution (/status, /processes, /pwd, /demo-task, /tasks, /cancel, /mock-agent, /answer, /attention)
  protocol.py            JARVIS_QUESTION: line parser
  workers/
    mock_worker.py       Deterministic mock interactive subprocess (progress → question → stdin read → complete)
  static/                HTML, CSS, JS frontend
tests/
  test_tasks.py          Pytest test suite for task management (8 tests)
  test_questions.py      Pytest test suite for question protocol and interactive workflow (16 tests)
```

## Known Limitations

- No authentication — anyone on the network can connect
- No TLS — WebSocket is plain WS, not WSS
- Only the predefined `/demo-task` and `/mock-agent` subprocesses (no arbitrary shell execution)
- `/processes` uses PowerShell (Windows-only)
- History is stored in a local SQLite file (`jarvis.db`)
- No AI, voice, push notifications, screenshots
- Events and questions tables grow unbounded (no rotation)
- Answer delivery via stdin works only on Windows; Unix may require different stdin handling for subprocesses
- Worker subprocess stdin write is best-effort; if the process has already consumed the question and moved on, the answer may be ignored
- Two concurrent workers each block on `sys.stdin.readline()` — answering one worker's question while the other is also waiting could theoretically write to the wrong stdin if a race condition occurs (mitigated by locking in `answer_question`)
- Mock worker uses fixed delays (1s normal, 0.1s test mode); a real worker would have variable timing
- No timeout for unanswered questions — a task can remain in `waiting_for_user` indefinitely
- No way to retract an answer once submitted
